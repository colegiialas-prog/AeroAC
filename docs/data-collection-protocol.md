# Aero AC — протокол сбора датасета

Инструкция для человека, который записывает реальные сессии. От качества этих записей зависит
всё остальное: модель, пороги, оценка false positives и решение о допуске.

Главный принцип: **одна длинная запись — это не большой датасет.** Нужны независимые игроки,
конфигурации и сессии. Тысяча окон одного игрока измеряет, насколько хорошо модель запомнила
этого игрока.

Смежное: [формат датасета](dataset.md), [ML pipeline](../ml/README.md),
[допуск модели](model-promotion.md).

## Подготовка сервера

```yaml
neural:
    enabled: true
    collection:
        enabled: true
```

`/aero reload`. Остальные стадии (`inference`, `risk`, `mitigation`) при сборе датасета
держать **выключенными**: предсказания модели не должны влиять на то, что записывается, а
mitigation прямо портит запись, отменяя удары.

Проверить:

```text
/neural status          collection=true, inference=false, risk=false, mitigation=false
```

Телеметрия начинается с первой атаки игрока и прекращается через `idle-timeout-seconds` без боя.
Открывать запись до боя нормально: кадры пойдут с первого удара.

## Команды записи

```text
/neural dataset start <player> legit [client] [configuration] [notes...]
/neural dataset start <player> cheat <family> [client] [configuration] [notes...]
/neural dataset stop <player>
/neural dataset status
```

Примеры:

```text
/neural dataset start Alice legit vanilla sens-high box-pvp
/neural dataset start Bob   cheat aimassist liquidbounce smooth-low fov-30-manual-lab
```

`client` и `configuration` — не косметика: по ним строится unknown-client split и по ним же
считается концентрация датасета. Пустое поле `configuration` превращается в `default` и склеивает
разные настройки в одну группу.

Имя игрока выбирает сессию операционно и **не попадает** ни в файлы записи, ни в признаки модели:
в metadata пишется HMAC-псевдоним.

## Что записывать: LEGIT

Цель — покрыть то, из-за чего честный игрок может выглядеть подозрительно. Минимум по каждому
пункту несколько **разных людей**, а не один человек, играющий по-разному.

```text
игроки          не менее 8-10 разных человек; чем больше, тем осмысленнее FPR
навык           слабые, средние и заведомо сильные PvP-игроки
sensitivity     низкая, обычная, высокая (крайние значения обязательно)
ping            локальный, ~50 мс, ~150 мс, ~250 мс и выше
protocol        1.8, современные версии, и всё, что реально ходит на сервер
клики           обычные, jitter, butterfly, drag
стиль           tracking, резкие flick shots, бой в толпе, бой с одной целью
условия         лаги сервера, рывки сети, бой на разной дистанции и высоте
```

Отдельно ценны записи, которые заведомо тяжелы для детектора: сильный игрок с низкой
sensitivity и плавным трекингом выглядит ближе всего к aim assist. Такие сессии — hard negatives,
и они важнее ещё одного часа обычного боя.

Длительность: сессии по 10–30 минут реального боя. Одна сессия на игрока за заход; несколько
коротких независимых сессий лучше одной длинной.

## Что записывать: CHEAT

```text
client families не менее 3-4 разных клиентов; иначе unknown-client benchmark невозможен
configurations  для каждого клиента несколько настроек, записанных отдельными сессиями
strength        слабая, средняя, сильная помощь
FOV             узкий и широкий
smoothing       минимальное и максимальное
randomization   включённое и выключенное
активация       постоянная и редкая/частичная (assist только на части ударов)
```

Самое ценное здесь — **слабые конфигурации**: низкая скорость наводки, высокое сглаживание,
маленький FOV, редкая активация. Сильный чит детектируется легко и мало что доказывает. Именно
слабые настройки определяют, где проходит реальная граница, и именно они станут hard positives.

Обязательно: одна configuration = одна сессия. Нельзя переключать настройки внутри записи —
метка сессии описывает её целиком.

`family` на текущем этапе — `aimassist`. Первая модель решает задачу `LEGIT vs AIM_ASSIST`;
AutoClicker, Scaffold, Movement и Velocity сейчас не собираются и не обучаются.

## Чего делать нельзя

* Записывать LEGIT и CHEAT **разными способами**: другой сервер, другая версия плагина, другое
  время суток, другой тип арены. Любое такое различие модель выучит вместо поведения, и
  `STRUCTURAL_LEAKAGE` в feature audit поймает не все такие случаи.
* Ставить метку по предсказанию модели или по срабатыванию Grim. Production-записи остаются
  `UNLABELED`, и pipeline на них падает с явным сообщением.
* Считать одну длинную запись большим датасетом.
* Записывать CHEAT на том же игроке и в той же сессии, где до этого шёл LEGIT.
* Собирать только сильные читы и только среднего легита.

## После записи

Каждый раз, перед любым обучением:

```bash
cd ml
python -m aeroml.tools.audit_dataset <dataset-root> --features --json reports/audit.json
```

Читать в отчёте прежде всего:

```text
Quality        сколько GOOD / REVIEW / UNUSABLE и по каким причинам
Coverage       сколько игроков, клиентов, конфигураций, версий протокола
CHEAT distribution  не состоит ли корпус фактически из одной настройки одного клиента
LEGIT distribution  распределение ping, sensitivity-следов, длительности, частоты атак
Warnings       предупреждения о концентрации
Feature audit  ALWAYS_MISSING / CONSTANT / STRUCTURAL_LEAKAGE / SEPARABLE
```

`UNUSABLE` и `REVIEW` разбирать вручную. Инструмент ничего не удаляет: список причин —
это то, что нужно исправить в следующем заходе записи, а не мусор для автоматической чистки.

`STRUCTURAL_LEAKAGE` в feature audit означает, что канал известен в одном классе и отсутствует в
другом: LEGIT и CHEAT прошли разными путями записи. Это надо исправлять в процедуре сбора, а не
в модели.

## Минимальный объём

Точные цифры зависят от того, какой FPR предполагается заявлять, и выводятся, а не назначаются:

```text
FPR 0.1%    ~10 000 legit-окон
FPR 0.01%   ~100 000 legit-окон
FPR 0.001%  ~1 000 000 legit-окон
```

`evaluate` считает это сам (`negatives_needed`) и помечает оценку `reliable: 0`, если окон
меньше. Одно attack-окно — один удар с полной историей, так что порядок величины по времени
зависит от темпа боя; ориентироваться следует на счётчик `attack windows` в аудите, а не на часы.

Для unknown-client benchmark нужно **минимум два** client family, и чем больше, тем честнее:
одна held-out семья из двух означает, что половина cheat-корпуса уходит в test.

## Ручная проверка и golden set

Регрессионный набор состоит из записей, которые человек посмотрел и подтвердил:

```bash
python -m aeroml.tools.audit_dataset <dataset> --write-review-candidates reports/candidates.json
python -m aeroml.tools.review_session <dataset> ../datasets/manifests/golden-v1.json \
    --session <sessionId> --expected-label LEGIT \
    --reviewer <псевдоним> --notes "что именно было видно в записи"
```

Кандидат — это ещё не проверка. `review_session` записывает sha256 записи, имя проверяющего,
время и заметку; синтетические сессии он отвергает. Заметка должна содержать независимое
наблюдение («смотрел запись целиком, игрок промахивается при смене цели»), а не оценку модели.

Сырые записи в публичный репозиторий не коммитить: это персональные данные игроков, которые их
произвели. В репозитории живёт только манифест.

## Порядок одного захода

```text
1. проверить /neural status: collection on, inference/risk/mitigation off
2. открыть запись на игрока с точными client и configuration
3. отыграть 10-30 минут реального боя без смены настроек
4. /neural dataset stop, дождаться CLOSED в /neural dataset status
5. запустить audit_dataset и прочитать Quality и Warnings
6. разобрать REVIEW и UNUSABLE, при необходимости переписать сессию
7. для регрессионного набора: посмотреть запись и провести её через review_session
```
